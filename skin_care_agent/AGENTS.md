# Skin Care Agent 工作规则

## 会话启动

处理本项目的产品、设计、代码或测试任务前，按顺序读取：

1. `project_background.md`
2. `design/product/skin_care_app_mvp_spec.md`
3. `docs/current_status.md`
4. `docs/current_status.md` 指定的唯一 ACTIVE 实施计划；没有 ACTIVE 计划时，不得沿用历史计划

历史资料已经从当前 MVP fork 清除。需要追溯早期设想、第二版完整设计、旧原型或旧迁移计划时，查看 Git 历史或外部备份，不要从记忆恢复需求。

## 信息源优先级

1. `design/product/skin_care_app_mvp_spec.md` 决定当前产品范围、行为、数据语义、AI 边界和验收。
2. ACTIVE 实施计划只能细化 MVP，不能新增产品决策。
3. `docs/current_status.md` 记录经代码、测试、迁移或 Git 验证的实现状态。
4. 当前代码、测试和迁移证明“已经实现什么”，不能决定“产品应该做什么”。

发现冲突时，列出冲突和来源，以 MVP 规格为准并修正下游材料。不要静默合并，也不要补充未经确认的需求。

## 进度记录

`docs/current_status.md` 是唯一当前进度视图。完成一个可独立验证的切片或子步骤后，更新其中的：

- 已验证实现；
- 验证命令和结果；
- 当前缺口或阻塞；
- 唯一 ACTIVE 计划和下一步。

它保存当前快照，不追加长篇会话流水。历史由 Git 提供。没有代码、测试、数据库迁移或 Git 证据时，使用“待验证”，不能写成“已完成”。

## 开发边界

- 默认按契约优先的端到端纵向切片推进。
- 不按技术层整体重写，也不让静态 Mock 页面代替持久化闭环。
- 旧三视角、皮肤指数、Patch lineage、旧趋势和聊天代码属于 legacy；只有切片明确需要时才修改或隔离。
- 不擅自安装依赖、执行数据库迁移、删除用户数据或提交 Git 变更。
- 修改后按风险运行测试和静态检查，并记录验证结果。
- 使用中文回复，文件路径优先写成相对于项目根目录的路径。

## 回答质量与表达

你的职责是解决用户真正的问题，而不是展示你知道多少。

回答前先判断：

1. 用户真正想解决什么？
2. 最关键的结论是什么？
3. 哪些事实或证据足以支撑这个结论？
4. 用户接下来需要做什么？

不要输出上述分析过程，直接给出提炼后的结果。

### 表达要求

- 开头直接给出核心判断、问题本质或最终结论。
- 优先指出最关键的 1～3 个问题，按影响大小排列。
- 说明问题时使用“现象 → 原因 → 影响 → 建议”；不需要的环节可以省略。
- 用具体事实、代码位置、数据或因果关系支撑判断，避免空泛评价。
- 区分事实、推断和建议；存在不确定性时明确指出不确定在哪里。
- 回答长度由问题复杂度决定。复杂问题可以详细，但每一段都必须提供新的有效信息。
- 问题已经回答清楚后立即停止，不为显得全面而继续扩写。

### 删除以下内容

- 对用户问题的重复转述。
- 与当前结论无关的背景知识。
- 同一观点的换词重复。
- 正确但没有实际帮助的常识。
- 套话、铺垫、礼貌性废话和机械总结。
- 没有证据支持的泛泛判断。
- 用户没有询问的延伸话题、替代方案和教程。
- 为凑结构而添加的标题、列表、总结和“下一步”。

判断一句话是否应该保留：删除它以后，如果不会影响结论、证据或行动，就删除。

### 针对不同任务

- 分析问题：先指出问题本质，再给关键依据。
- 代码审查：说明问题位置、触发条件、实际影响和最小修改方案。
- 方案比较：只比较会影响选择的差异，最后给出明确推荐。
- 总结材料：提炼结论、分歧、风险和待办，不按原文顺序复述。
- 完成任务：说明结果、关键改动和验证情况，不写工作流水账。
- 简单问题：直接回答，不强行套用完整结构。

用户明确要求详细讲解时可以展开，但仍需保持信息密度，避免重复和堆砌。
